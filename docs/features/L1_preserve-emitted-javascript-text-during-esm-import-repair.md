# L1: Preserve emitted JavaScript text during ESM import repair

## Goal

Preserve JavaScript program data when repairing extensionless ESM imports in built workspace artifacts. Build repair must change actual module specifiers while leaving strings, template text and comments intact.

## Scope

- In: syntax-aware relative import/export specifier edits in scripts/lib/build.ts and regression/integration tests in scripts/tests/build.test.ts, reusing the installed TypeScript parser and existing resolver.
- Out: release workflow changes, dependency upgrades, declaration-file rewriting, source transpilation, package API changes and formatting emitted programs.

## Acceptance Criteria

```gherkin
Feature: Safe ESM import repair
  Scenario: AC1 — Non-module text survives repair
    Given emitted JavaScript with a relative import and matching import-shaped string, template and comment text
    When the build repair runs against an emitted sibling module
    Then the actual import resolves with a JavaScript extension and all non-module text is preserved byte for byte

  Scenario: AC2 — Resolver semantics stay compatible
    Given direct-file and directory-index emitted modules alongside existing extensions and unresolved modules
    When the build repair runs twice
    Then known extensionless relative modules resolve correctly and the second run changes no bytes

  Scenario: AC3 — Runtime output and gates verify the repair
    Given a repaired temporary dist entry exporting import-shaped text and loading a sibling
    When the entry is imported and the repository gates run
    Then the original text is preserved and the focused tests, spur-check and build succeed
```
