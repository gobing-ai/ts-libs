# M: Reusable browser profile automation

## Goal

Projects can run user-authenticated browser automation with a dedicated reusable profile and an explicit site-owned session check.

## Scope

**In scope**

- A published ts-libs browser-session package with typed Playwright context and page access.
- User-driven headed login into a caller-selected dedicated profile directory.
- Later headless use of the same profile, with caller-owned authentication readiness checks and predictable cleanup.
- Clear failures and documentation for unavailable browser runtime, invalid/busy/expired profiles, and sensitive session data.

**Out of scope**

- Site selectors or workflows, browser anti-detection, CAPTCHA bypass, password storage, and application publishing semantics.
- `storageState` export/import and remote CDP attachment.
- New implementations for X, Substack, Medium, or other individual sites.

## Acceptance Criteria

```gherkin
Feature: Reusable browser profile automation

  @core
  Scenario: R1 — A user can sign in once with a dedicated visible browser profile
    Given a caller-selected profile path and a site-owned login readiness predicate
    When the user signs in through a visible Chromium window
    Then the operation reports success only after the predicate passes and retains the session in that profile

  @core
  Scenario: R2 — An authenticated profile can drive a later headless browser callback
    Given a profile from an earlier completed login
    When a later process opens it headlessly and runs a page callback
    Then the callback receives typed Playwright page and context access and the context closes afterward

  @core
  Scenario: R3 — Missing, busy, expired, and timed-out profiles fail without a false authenticated result
    Given a missing or busy profile, an expired site session, or a login that never completes
    When the corresponding browser operation runs
    Then it reports the specific recoverable failure without claiming an authenticated session

  @core
  Scenario: R4 — The browser package builds and loads independently of knowledge-kit
    Given a consumer that depends only on the new ts-libs package and its declared Playwright peer
    When the package builds and the consumer imports its public API
    Then typed browser-session operations are available without knowledge-kit code or defaults
```
