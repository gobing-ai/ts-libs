# O2: Decision maker fallback chains, shadow makers and fallback diagnostics

## Goal

Let downstream consumers route one catalog decision across several makers and observe why it fell back, without giving up the hub's never-reject fallback contract (ADR-033, ADR-040): an ordered maker fallback chain that advances on backend failure, a shadow maker that is asked beside the primary on live traffic without changing the served answer, and the caught error carried on every failure-reason fallback result.

## Scope

**In scope**

- Fallback diagnostics: `error: { name, message }` (`DecisionErrorInfo`) on `no-backend` / `timeout` / `error` fallback results.
- Maker chains: `maker` as a name or a non-empty ordered list in the catalog (decision and `defaults`), the JSON schema, and `DecideOptions.maker`; advance only on backend failure; `attempts[]` when more than one maker was tried; descriptor `makers`.
- Shadow maker: `shadow` on a decision and on `DecideOptions`; asked concurrently on the same request; reported as `result.shadow`; never changes the served answer and never throws.
- ADR-040, `docs/design/ai-decision-catalog.md` § Maker chains, shadow and diagnostics, and the ai-decision README.

**Out of scope**

- Advancing the chain on `low-confidence` (confidence cascades), confidence calibration, sampling-rate or adaptive routing.
- Shadow callbacks, queues or background work that outlives `decide`; persistence of attempts or shadow outcomes (consumers log them).
- Retrying the same maker, and any change to the driver packages or the neutral decision contract in `ts-ai-runner`.
- Downstream adoption in Spur or knowledge-kit (their own tasks).

## Acceptance Criteria

```gherkin
Feature: Decision maker fallback chains, shadow makers and fallback diagnostics

  @core
  Scenario: R1 — Failure fallbacks carry the caught error
    Given a hub whose maker for decision "category" rejects with DecisionTimeoutError "fm timed out after 30000ms"
    When decide is called for "category"
    Then the result has source default, reason timeout and the declared fallback value
    And the result error has name DecisionTimeoutError and message "fm timed out after 30000ms"
    And an accepted or low-confidence result has no error field
    And an error message longer than 500 characters is cut to 500 characters

  @core
  Scenario: R2 — A maker chain advances only on backend failure
    Given a decision whose maker is the list fm-local, typesafe
    And fm-local fails to construct with DecisionConfigError
    When decide is called
    Then typesafe is asked and its accepted answer is returned with maker typesafe
    And attempts lists fm-local with reason no-backend and its error, then typesafe with reason accepted
    And when fm-local instead answers below the confidence floor, the result is low-confidence from fm-local and typesafe is never asked

  @core
  Scenario: R3 — An exhausted chain returns the declared fallback with the last failure
    Given a decision whose maker list is fm-local, laya-local and both fail with backend errors
    When decide is called
    Then the result is the declared fallback with source default
    And reason, maker and error come from laya-local, the last maker tried
    And attempts lists both makers in order
    And decide does not reject

  @core
  Scenario: R4 — Chains are validated like single names
    Given a catalog whose decision maker list names an unregistered maker or is empty
    When the catalog is loaded into a hub
    Then load throws DecisionCatalogError naming the decision and registers nothing from that catalog
    And a per-call maker list containing an unregistered name throws UnknownDecisionMakerError before any backend call
    And describe returns maker as the first chain name and makers as the full chain

  @core
  Scenario: R5 — A shadow maker is observed but never served
    Given a decision with maker typesafe and shadow laya-local
    When decide is called
    Then both makers are asked with the same rendered request
    And value, source, reason and maker come only from typesafe
    And result shadow reports laya-local with its value, confidence, reason and duration
    And when laya-local rejects, result shadow carries reason and error and decide still resolves with the typesafe answer

  @edge
  Scenario: R6 — Single-maker decisions are unchanged
    Given a catalog that names one maker per decision and no shadow
    When the existing ai-decision test suite runs after the change
    Then every existing test passes unchanged
    And results carry neither attempts nor shadow
```
